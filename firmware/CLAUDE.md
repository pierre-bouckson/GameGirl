# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

GameGirl: a handheld console on an STM32F429ZIT6 (currently developed on an STM32F429I-DISC1 board) with a 240×320 ILI9341 LCD, analog joystick and buttons. Bare-metal C on the STM32 HAL, no RTOS. The repo root also holds `PCB/` and `docs/` (datasheets); all code lives in `firmware/`.

## Build / flash / debug output

Run from `firmware/`:

```sh
make                 # builds build/GameGirl.{elf,hex,bin} with arm-none-eabi-gcc (DEBUG=1, -Og)
make GCC_PATH=/path  # if the toolchain isn't on PATH
make clean
make flash           # OpenOCD + ST-LINK: program, verify, reset (OPENOCD_BOARD ?= board/stm32f429disc1.cfg)
```

There are no tests or linter. "Compiles cleanly" means no errors and no warnings from `make` (`-Wall`).

`printf` goes to USART1 at 115200 8N1 (`__io_putchar` in `Src/main.c`, stdout set unbuffered). On the DISC1 this is the ST-LINK virtual COM port.

The IDE's clangd shows false errors (`'main.h' file not found`, unknown HAL types) because include paths exist only in the Makefile and there is no `compile_commands.json`. Trust `make`, not those diagnostics.

## CubeMX-generated code

`GameGirl.ioc` is the source of truth for peripheral configuration (clocks, ADC, DMA, LTDC, FMC, SPI5, I2C3, USART1, GPIO). `Src/main.c`, `Src/stm32f4xx_hal_msp.c`, `Src/stm32f4xx_it.c`, `Inc/*` and the `Makefile` are regenerated by CubeMX:
- Hand-written code in those files must stay inside `/* USER CODE BEGIN ... */ /* USER CODE END ... */` blocks, or it is lost on regeneration.
- Change peripheral settings in the `.ioc` (then regenerate), not only in `MX_*_Init()`.
- The Makefile has hand-added parts that regeneration may drop: the `Engine/Src/*.c` and `Game/*/*.c` wildcards in `C_SOURCES`, `Drivers/ili9341` and `Drivers/Discovery` sources and includes, the `C_INCLUDES += $(addprefix -I,$(wildcard Game/*))` line (kept outside the CubeMX block on purpose), and the `flash` target. Check them after regenerating.

## Architecture

Three layers:

- **Hardware/HAL** (`Src/`, `Inc/`, `Drivers/`): CubeMX init, plus the SDRAM command sequence (`SDRAM_InitSequence` in `main.c`, which must run before any display call). `Drivers/ili9341` is ST's BSP panel driver, and `Drivers/Discovery` is the DISC1 BSP it depends on for SPI5.
- **Engine** (`Engine/`): reusable services for games.
  - `display`: double-buffered framebuffer. Two 240×320 RGB565 buffers in external SDRAM at `0xD0000000` and `0xD0000000 + 150 KB` (FMC bank 2). The LTDC continuously DMAs the front buffer to the panel over parallel RGB; SPI5 only configures the ILI9341 in `ili9341_Init()`. All `display_draw_*` functions write to the back buffer, and nothing becomes visible until `display_swap()`. That call reloads the LTDC address at vertical blanking and waits for it before swapping, so it blocks for up to one frame. Coordinates are in pixels.
  - `font8x8`: 8×8 bitmap font, so text grids are `LCD_W/FONT_W` × `LCD_H/FONT_H` = 30 × 40 cells.
  - `input`: `selection_joy()` turns raw 12-bit joystick values (center ≈ 2048, dead zone ±500) into a `joy_mv_t` direction of -1/0/1 per axis.
- **Games** (`Game/<name>/`): each game is a folder, automatically compiled and added to the include path by the Makefile wildcards. `menu/` is the game-selection screen: the whole screen is a 30×40 ASCII grid (`menu[][]` in `interface.c`, zone coordinates in `interface.h`), and `menu.c` draws it cell by cell with `display_draw_char`, coloring each cell by zone (title `#` and icon letters become solid color blocks, the selected tile gets an accent-colored frame and name bar). Tiles are listed in `tile_pos[]`, in `game_id_t` order (2 per row, 3 rows). Each joystick X tilt moves the selection one row (-1 = down), and Y picks the column (1 = right). The PA0 button (EXTI0 sets `button_pressed` in `main.c`) calls `start_game()`, which runs the selected game's blocking entry point and returns to the menu.
  - `puissance4/`: `menu_puissance4()`, a C port of the terminal Connect 4 (Bot / 2 player), same ASCII look.
  - `rocket/`: `menu_rocket()`, Rocket Space ported from the STM32F0 exam project. It emulates the original 64-column scrolling terminal, 3 px per column. The joystick Y axis gives the absolute position, and holding PA0 boosts speed.
  - Source file names must be unique across all folders, because the Makefile puts every `.o` in `build/` flat. Prefix them with the game name (`p4_*.c`, `rocket_*.c`).
  - `snake/`: `game()`, Snake on a 30×30 cell grid, best score saved in flash sector 22 (2048 uses sector 23, Tetris sector 21).
  - `pong/`: `menu_pong()`, vertical Pong against a bot (player at the bottom, analog joystick Y axis). The ball and paddles move per pixel with float positions, independent of the 8×8 cell grid, so the bounce angle follows the impact point on the paddle (0° at the center, up to ±60° at the edge). A first screen picks the bot level (FACILE/MOYEN/DIFFICILE: paddle speed, aim error, and landing prediction for DIFFICILE). First to 5 points wins; PA0 during a game returns to the menu.
  - `tetris/`: `menu_tetris()`, Tetris (work in progress). The 10×20 board is `tab[x][y]` with y = 0 at the bottom, 0 = empty, > 0 = landed block, < 0 = block of the falling piece, and |value| - 1 is the shape (`shape_id_t`), which picks the color. `print_tab()` draws each board cell as a 2×2 block of characters (16 px), so the board fills the screen height, with the info panel on the right. Piece shapes are 4×4 grids of 0/1 in `shape.c`. The joystick moves (Y), rotates (X up) and soft-drops (X down), and PA0 also rotates, so a game only ends at game over. Pieces come from a 7-bag, the fall speeds up every 10 lines, and the best score is saved in flash sector 21.

### Joystick acquisition

ADC1 scans channel 5 (PA5, X) and channel 13 (PC3, Y) in continuous mode. DMA2 Stream0, in circular mode with half-word transfers, writes the results into `volatile uint16_t joy_adc[2]` in `main.c`, where rank order gives `[0]` = X and `[1]` = Y. The DMA is started once with `HAL_ADC_Start_DMA` and never stopped: read `joy_adc` directly, and never call `HAL_ADC_ConfigChannel`/`HAL_ADC_Stop` at runtime, which would break the scan sequence. Raw values are noisy, so compare directions from `selection_joy()`, not raw ADC values.
