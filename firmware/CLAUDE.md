# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

GameGirl: a handheld console on an STM32F429ZIT6 (currently developed on an STM32F429I-DISC1 board) with a 240×320 ILI9341 LCD, analog joystick and buttons. Bare-metal C on the STM32 HAL, no RTOS. The repo root also holds `PCB/` and `docs/` (datasheets); all code lives in `firmware/`.

## Build / flash / debug output

Run from `firmware/`:

```sh
make                 # builds build/GameGirl.{elf,hex,bin} with arm-none-eabi-gcc (DEBUG=1, -Og)
make GCC_PATH=/path  # if the toolchain isn't on PATH
make clean
make flash           # OpenOCD + ST-LINK: program, verify, reset (OPENOCD_BOARD ?= board/stm32f429disc1.cfg)
```

There are no tests or linter. "Compiles cleanly" means no errors and no warnings from `make` (`-Wall`).

`printf` goes to USART1 at 115200 8N1 (`__io_putchar` in `Src/main.c`, stdout set unbuffered). On the DISC1 this is the ST-LINK virtual COM port.

The IDE's clangd shows false errors (`'main.h' file not found`, unknown HAL types) because include paths exist only in the Makefile and there is no `compile_commands.json`. Trust `make`, not those diagnostics.

## CubeMX-generated code

`GameGirl.ioc` is the source of truth for peripheral configuration (clocks, ADC, DMA, LTDC, FMC, SPI5, I2C3, USART1, GPIO). `Src/main.c`, `Src/stm32f4xx_hal_msp.c`, `Src/stm32f4xx_it.c`, `Inc/*` and the `Makefile` are regenerated by CubeMX:
- Hand-written code in those files must stay inside `/* USER CODE BEGIN ... */ /* USER CODE END ... */` blocks, or it is lost on regeneration.
- Change peripheral settings in the `.ioc` (then regenerate), not only in `MX_*_Init()`.
- The Makefile has hand-added parts that regeneration may drop: the `Engine/Src/*.c` and `Game/*/*.c` wildcards in `C_SOURCES`, `Drivers/ili9341` and `Drivers/Discovery` sources and includes, the `C_INCLUDES += $(addprefix -I,$(wildcard Game/*))` line (kept outside the CubeMX block on purpose), and the `flash` target. Check them after regenerating.

## Architecture

Three layers:

- **Hardware/HAL** (`Src/`, `Inc/`, `Drivers/`): CubeMX init, plus the SDRAM command sequence (`SDRAM_InitSequence` in `main.c`, which must run before any display call). `Drivers/ili9341` is ST's BSP panel driver, and `Drivers/Discovery` is the DISC1 BSP it depends on for SPI5.
- **Engine** (`Engine/`): reusable services for games.
  - `display`: double-buffered framebuffer. Two 240×320 RGB565 buffers in external SDRAM at `0xD0000000` and `0xD0000000 + 150 KB` (FMC bank 2). The LTDC continuously DMAs the front buffer to the panel over parallel RGB; SPI5 only configures the ILI9341 in `ili9341_Init()`. All `display_draw_*` functions write to the back buffer, and nothing becomes visible until `display_swap()`. That call reloads the LTDC address at vertical blanking and waits for it before swapping, so it blocks for up to one frame. Coordinates are in pixels. The panel is mounted upside down on the GameGirl PCB, so `DISPLAY_ROTATE_180` (`display.h`, 1 by default, 0 for the DISC1) makes `display_draw_pixel` write the buffer in reverse order; every drawing call goes through it, so games never touch the framebuffer directly.
  - `font8x8`: 8×8 bitmap font, so text grids are `LCD_W/FONT_W` × `LCD_H/FONT_H` = 30 × 40 cells.
  - `backlight`: PB4 = TIM3_CH1, 20 kHz PWM (TIM3 clock 64 MHz, ARR 3199) on the TPS61165 CTRL pin. Levels 1..10 (duty = level × 10 %; 0 would shut the backlight off). `backlight_init()` runs once in `main.c` and restores the level saved in flash sector 19; `backlight_save()` writes it back only if it changed.
  - `battery`: `battery_mv()` averages the DMA buffer and feeds a moving average of VSW, read on PA1 through the R7/R8 100 kΩ divider (VBAT_SENSE = VSW / 2). VDDA is recomputed from VREFINT and its factory calibration, so the reading stays right even if the 3V3 rail is off. `battery_percent()` interpolates a Li-ion discharge curve; above `BATTERY_USB_MV` (4.35 V) VSW is VBUS minus the D1 diode, so `battery_on_usb()` is true.
  - `buzzer`: passive MLT-8530 buzzer on PB14 = TIM12_CH1 (AF9), driven at 50 % duty (0 = silent). `buzzer_init()` configures the pin and TIM12 itself (they are not in the `.ioc` yet). Non-blocking: `buzzer_play(melody)` starts a `note_t` array ending with `{0, 0}` (or `buzzer_tone(freq, ms)`), and `buzzer_tick()` advances it every ms from `HAL_IncTick`, which `buzzer.c` overrides (weak HAL function). Shared sounds: `SND_BOOT` (played at startup), `SND_MOVE`, `SND_SELECT`, `SND_BACK`, `SND_HIT`, `SND_POINT`, `SND_LOSE`, `SND_WIN`; every game uses them.
  - `game_exit`: the START button (PE4, active high, EXTI4 configured by `game_exit_init()`, handler in `game_exit.c` because PE4 is not in the `.ioc` yet) returns to the menu from anywhere in a game. `start_game()` runs games through `game_run()`, which does a `setjmp`; START only sets a flag, and `game_exit_poll()` does the `longjmp` back. It is called by `display_swap()` and by `HAL_Delay()`, which `game_exit.c` overrides, so every waiting loop in a game must go through one of them (`while (!button_pressed) HAL_Delay(1);`, never an empty busy-wait). START does nothing in the menu.
  - `input`: `selection_joy()` turns raw 12-bit joystick values (center ≈ 2048, dead zone ±500) into a `joy_mv_t` direction of -1/0/1 per axis.
- **Games** (`Game/<name>/`): each game is a folder, automatically compiled and added to the include path by the Makefile wildcards. `menu/` is the game-selection screen: the whole screen is a 30×40 ASCII grid (`menu[][]` in `interface.c`, zone coordinates in `interface.h`), and `menu.c` draws it cell by cell with `display_draw_char`, coloring each cell by zone (title `#` and icon letters become solid color blocks, the selected tile gets an accent-colored frame and name bar). Tiles (12×5 cells: border, 2 icon rows, name) are listed in `tile_pos[]`, in `game_id_t` order (2 per row, 4 rows; the 8th tile, `GAME_REGLAGES`, is the settings screen, not a game). The battery percentage (or `USB`) is drawn over the top frame at `BATTERY_ROW`/`BATTERY_COL`; `menu_tick()`, called on every 100 ms main-loop pass, measures the battery and redraws the menu only when that text changes. Each joystick X tilt moves the selection one row (-1 = down), and Y picks the column (1 = right). The PA0 button (EXTI0 sets `button_pressed` in `main.c`) calls `start_game()`, which runs the selected game's blocking entry point and returns to the menu.
  - `reglages/`: `menu_reglages()`, the settings screen. Joystick Y adjusts the backlight live (1 = right = brighter), and it shows the battery bar, percentage and voltage, refreshed every second. PA0 returns to the menu and saves the backlight level to flash (sector 19) if it changed.
  - `puissance4/`: `menu_puissance4()`, a C port of the terminal Connect 4 (Bot / 2 player), same ASCII look.
  - `rocket/`: `menu_rocket()`, Rocket Space ported from the STM32F0 exam project. It emulates the original 64-column scrolling terminal, 3 px per column. The joystick Y axis gives the absolute position, and holding PA0 boosts speed.
  - Source file names must be unique across all folders, because the Makefile puts every `.o` in `build/` flat. Prefix them with the game name (`p4_*.c`, `rocket_*.c`).
  - `snake/`: `game()`, Snake on a 30×30 cell grid, best score saved in flash sector 22 (2048 uses sector 23, Tetris sector 21, Flappy sector 20, the backlight level sector 19).
  - `pong/`: `menu_pong()`, vertical Pong against a bot (player at the bottom, analog joystick Y axis). The ball and paddles move per pixel with float positions, independent of the 8×8 cell grid, so the bounce angle follows the impact point on the paddle (0° at the center, up to ±60° at the edge). A first screen picks the bot level (FACILE/MOYEN/DIFFICILE: paddle speed, aim error, and landing prediction for DIFFICILE). First to 5 points wins; PA0 during a game returns to the menu.
  - `tetris/`: `menu_tetris()`, Tetris (work in progress). The 10×20 board is `tab[x][y]` with y = 0 at the bottom, 0 = empty, > 0 = landed block, < 0 = block of the falling piece, and |value| - 1 is the shape (`shape_id_t`), which picks the color. `print_tab()` draws each board cell as a 2×2 block of characters (16 px), so the board fills the screen height, with the info panel on the right. Piece shapes are 4×4 grids of 0/1 in `shape.c`. The joystick moves (Y), rotates (X up) and soft-drops (X down), and PA0 also rotates, so a game only ends at game over. Pieces come from a 7-bag, the fall speeds up every 10 lines, and the best score is saved in flash sector 21.
  - `flappy/`: `menu_flappy()`, Flappy Bird. The 240×256 px field (240 px of sky, 16 px of scrolling ground) sits under the title; the bird stays at a fixed x with a float y, and 3 recycled pipes scroll left, speeding up slightly with each pipe passed. PA0 or a joystick X tilt up flaps, so a game only ends at a collision. The best score is saved in flash sector 20.

### Joystick acquisition

ADC1 scans 4 channels in continuous mode: channel 5 (PA5), channel 13 (PC3), channel 1 (PA1, VBAT_SENSE) and VREFINT. DMA2 Stream0, in circular mode with half-word transfers, writes the results into `volatile uint16_t adc_values[ADC_NB_CHANNELS]` in `main.c` (declared in `main.h`), indexed by the `ADC_IDX_*` macros in `main.h` in rank order. The joystick is mounted rotated on the GameGirl, so PA5 (rank 0) is the game Y axis and PC3 (rank 1) the X axis: `ADC_IDX_JOY_Y` = 0, `ADC_IDX_JOY_X` = 1. The DMA is started once with `HAL_ADC_Start_DMA` and never stopped: read `adc_values` directly, and never call `HAL_ADC_ConfigChannel`/`HAL_ADC_Stop` at runtime, which would break the scan sequence. Raw values are noisy, so compare directions from `selection_joy()`, not raw ADC values.
